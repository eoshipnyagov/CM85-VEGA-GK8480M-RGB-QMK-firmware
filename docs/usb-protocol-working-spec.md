# KD85 Vega: рабочая спецификация USB vendor HID

Статический анализ `VEGA_vial_v1_01_20231201.bin`. Это не окончательная
документация протокола: названия команд даны только там, где их подтверждает
логика обработчика.

## Транспорт

| Свойство | Значение |
|---|---|
| USB канал | vendor/raw HID |
| Usage page | `0xFF60` |
| Usage | `0x61/0x62/0x63` |
| Input report | 32 байта |
| Output report | 32 байта |
| Основной обработчик | `0x08006F94` |
| Отправка ответа | `0x0800197C` |

Входной пакет локально обозначаем `data[0..31]`. Обработчик проверяет размер
`0x20`. Для основного vendor-пути команда выбирается из `data[1]`; при этом
`data[0]` участвует в предварительной проверке режима USB и не должен пока
считаться обычным номером команды.

## Верхний уровень

| `data[1]` | Ветка | Поля, подтверждённые дизассемблером |
|---:|---:|---|
| `0x00` | `0x080077C2` | ответ начинается с `0x06`; читает 8 байт из постоянного источника |
| `0x01` | `0x080077EA` | ответ начинается с `0xEC`; далее подготавливается 28-байтный ответ |
| `0x02` | `0x080077FC` | `data[2:3]` — индекс страницы; размер страницы 32 байта |
| `0x03` | `0x08007830` | `data[2:3]` используются как два аргумента чтения |
| `0x04` | `0x08007862` | использует `data[2]`, `data[3]`, `data[4]`, `data[5]`, `data[6]` |
| `0x05` | `0x08007892` | очищает 28 байт ответа значением `0xFF` |
| `0x06` | `0x080078C0` | возвращает служебные счётчики/состояние |
| `0x07` | `0x080078D4` | служебное состояние, таймеры и счётчики |
| `0x08` | `0x08007932` | сброс служебного состояния |
| `0x09` | `0x0800793A` | перебор таблицы записей по 16-битному ключу |
| `0x0A` | `0x0800797A` | поиск обработчика по 16-битному ключу |
| `0x0B` | `0x080079B0` | вызов найденного обработчика записи |
| `0x0C` | `0x08007A0C` | отдельная служебная операция `0x080031F0` |
| `0x0D` | `0x08007A12` | macro/storage поддиспетчер |

Поля с двоеточием записаны в порядке байт пакета: `data[2:3]` означает
`data[2]` и `data[3]`. Точный endian для каждой команды восстанавливается
отдельно: в некоторых ветках код явно собирает little-endian 16-битное число,
а в других передаёт байты в подфункцию без перестановки.

## Поддиспетчер `0x0D`

Третий байт `data[2]` выбирает подкоманду. Для подкоманд `3–6` четвёртый байт
`data[3]` — индекс от `0` до `31`, а запись имеет длину 10 байт.

```text
offset = base + 10 * data[3]
```

Наблюдаемые базы:

| Подкоманда | Действие | Адреса функций |
|---:|---|---|
| `0` | очистка/подготовка ответа | `0x08007A28` |
| `1` | формирование параметра | `0x08007A42` |
| `2` | преобразование 16-битных полей | `0x08007A64` |
| `3` | чтение 10 байт | `0x08007AC8`, `0x0800A0AC` |
| `4` | запись 10 байт | `0x08007AF0`, `0x08009FE8` |
| `5` | чтение альтернативного блока | `0x08007B2E`, `0x0800A0AC` |
| `6` | запись альтернативного блока | `0x08007B52`, `0x08009FE8` |

## Безопасный следующий эксперимент

Первым практическим тестом должен быть только запрос чтения, без записи и
без команд сброса:

```text
?? 0D 03 index 00 00 00 00 00 00 00 00 00 00 00 00
00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00
```

Здесь `??` пока намеренно оставлен неизвестным: значение `data[0]` зависит от
режима endpoint и должно быть подтверждено через реальный USB-трафик или
исходный Vial-клиент. До этого не следует отправлять пакеты записи (`0x09`,
`0x0B`, подкоманды `4` и `6`) на рабочую клавиатуру.

## Что это говорит об экране

В данном обработчике нет циклов передачи больших блоков, адресов кадров или
вызовов I2C/UART. Найденная flash-связь ограничена маленькими служебными
записями. Поэтому дисплейный протокол, если он есть, скорее всего находится
в другом USB endpoint callback, в отдельной ветке производителя или во втором
контроллере.

Дополнительная проверка усиливает этот вывод: raw-HID descriptor описывает
основной keyboard/Vial-интерфейс с 32-байтными input/output reports, но не
отдельный USB-интерфейс HFD80CP100. В текущем образе нет найденного пути
`vendor HID -> UART3` для больших блоков; UART3 используется прикладочно для
коротких статусных пакетов `[02,...]` и `[03,...]`. Поэтому загрузка GIF через
этот бинарник пока не подтверждена. Наиболее вероятны отдельный
производительский command path, другой режим/образ прошивки либо самостоятельное
USB-подключение второго контроллера через схему, которой не видно в WB32-образе.
