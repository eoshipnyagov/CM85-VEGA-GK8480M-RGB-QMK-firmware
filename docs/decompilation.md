# Декомпиляция прошивки

Для бинарника `VEGA_vial_v1_01_20231201.bin` введён воспроизводимый первый
проход:

```text
python tools/decompile_firmware.py firmware/original/VEGA_vial_v1_01_20231201.bin
```

Он строит каталог предполагаемых функций из:

- адресов активных векторов;
- целей прямых `BL`/`BLX` переходов;
- адресной базы `0x08000000` и Thumb-режима.

Имена пока имеют два уровня достоверности:

- подтверждённые роли: `reset_startup`, `svc_rtos`, `systick_rtos`;
- рабочие гипотезы: `irq_vector_NN` и `sub_XXXXXXXX`.

Полный машинный листинг генерируется отдельно через установленный ARM
`objdump`. Он сохраняется локально в `analysis-output/full-thumb-disassembly.txt`
и не включается в Git из-за размера.

Текущий запуск на образе дал `236` кандидатов на начало функций. Это верхняя
оценка: автоматический поиск по `BL` также захватывает отдельные ложные цели
из областей данных. После проверки прологов, ветвлений и `BX LR` каталог будет
сокращён до подтверждённых функций.

Из уже подтверждённых участков:

- `reset_startup` — копирование `.data`, очистка BSS и запуск таблиц
  инициализаторов;
- `svc_rtos` — работа с PSP/BASEPRI, часть системного переключения;
- `systick_rtos` — системный счётчик и обслуживание списка таймеров/ожиданий;
- `vector[30] -> 0x08009959` — активный IRQ-кандидат, работающий с флагами
  состояния и рабочей структурой;
- `vector[31] -> 0x08008BD1`, `vector[40] -> 0x08009601`,
  `vector[42] -> 0x08009741`, `vector[46] -> 0x08009DB1`,
  `vector[48] -> 0x08009DC5`, `vector[51] -> 0x08008BD5` — следующие
  периферийные IRQ-кандидаты для разметки.

## Первая карта периферийных связок

Скрипт [`tools/peripheral_xrefs.py`](../tools/peripheral_xrefs.py) разрешает
PC-relative `LDR` к реальным адресам периферии. На текущем образе найдено 57
таких ссылок:

| Область образа | Наблюдение | Рабочая гипотеза |
|---|---|---|
| `0x080061E0–0x08006300` | RCC, I2C2, UART1, UART3, QSPI | общая инициализация HAL и структур драйверов |
| `0x0800661C–0x08008110` | RCC, USB, GPIOC | низкоуровневый системный/USB слой |
| `0x08008A44–0x08009A14` | многочисленные USB-регистры | USB peripheral driver, включая endpoint/status логику |
| `0x0800A57C–0x0800A742` | десять ссылок на GPIOB | GPIO-конфигурация и служебные операции с портом |

Особенно показателен кластер около `0x080092EA–0x080095F2`: там есть
множество операций с регистрами USB, но также таблицы состояний и вызовы
через указатели. Это главный кандидат для восстановления USB/Vial пути.

Участок `0x0800A57C` вызывает низкоуровневую функцию примерно с параметрами
`(GPIOB, mask, mode/config)` и использует маски `0x08`, `0x20`, `0x10`, затем
`0x1A82` и `0x0282`. Пока корректнее назвать его `gpiob_config_candidate`:
сам по себе этот фрагмент не доказывает matrix scan.

## Поиск matrix scan

Первичная проверка не подтвердила сканер в найденных GPIO-кластерах:

- `0x080068BE` и `0x08006AD6` — настройка GPIOC с регистрами конфигурации;
- `0x0800A58A` — настройка GPIOB через маски и режимы;
- `0x08008B92` — общий низкоуровневый GPIO-конфигуратор;
- `0x08008B18` — объектный транспортный код, связанный с USB, а не GPIO-сканер.

Перспективен диапазон `0x080067D0–0x08006A60`. В нём есть циклы на 17 и 6
элементов по таблицам указателей, а также временная работа с GPIOA. Пока это
выглядит как аппаратная/драйверная инициализация, но именно здесь могут быть
таблицы линий платы. Следующий критерий проверки — наличие внутри вызываемых
функций чтения входного регистра и повторного прохода с изменением номера
строки. До такой проверки называть участок `matrix_scan` преждевременно.

### Подтвержденные таблицы матрицы

Дальнейший разбор literal pool показал, что адреса `0x08006A88` и
`0x08006A8C` указывают на две таблицы GPIO-дескрипторов:

```text
columns[17] = {
    C1, C2, C3, A0, A1, A2, A3, A4, A5, A6, A7,
    C4, C5, B0, B1, B2, B10, B11, B12, B13
};

rows[6] = { B15, C6, C7, C8, C9, B14 };
```

В бинарнике это хранится как адреса вида `0x40000801` или `0x4000040F`:
база GPIO плюс номер вывода. Первая таблица содержит ровно 17 элементов,
вторая ровно 6. Циклы в `0x08006770` обходят их соответственно 17 и 6 раз,
передавая каждый дескриптор в `0x08002A6E`.

`0x08002A6E` извлекает младшие четыре бита как номер вывода, очищает их для
получения базы порта и вызывает `0x08008B92` с маской и режимом GPIO. Это
подтверждает назначение таблиц как аппаратной конфигурации клавиатурной
матрицы, а не случайной таблицы периферии.

Уровень уверенности:

- наличие двух наборов GPIO: **точно**;
- размеры 17×6: **точно**;
- назначение как columns/rows: **очень вероятно**, совпадает с порядком
  циклов и физическим форматом KD85;
- полярность диодов и точная функция сканирования: ещё нужно подтвердить по
  чтению входов и обработке debounce.

### Энкодер и служебные режимы KD85

Матрицу считаем источником обычных клавиш. Отдельно учитываем:

- энкодер громкости с двумя фазовыми входами `ENC_A` и `ENC_B`;
- кнопку на валу энкодера, если она электрически присутствует на плате;
- Fn-сочетания для эффектов подсветки, яркости и переключения Win/Mac.

Два фазовых сигнала энкодера не следует добавлять в таблицу `17×6`: они могут
быть отдельными GPIO главного MCU, линиями вторичного контроллера или событиями,
передаваемыми по шлейфу. В бинарнике их будем искать по двум взаимосвязанным
входам, обработке переходов состояний и последующем изменении значения
громкости/режима.

Сочетания подсветки и Win/Mac — не отдельные физические клавиши, а обработка
слоёв/keymap. Для них нужны восстановление keymap-таблиц, layer state и
числовых action-кодов.

## Как будем давать имена

Имя закрепляется только после проверки нескольких признаков:

| Рабочее имя | Что должно подтвердиться |
|---|---|
| `usb_irq` | доступ к USB-регистрам, endpoint/status-поля, вызовы HID-логики |
| `vendor_hid_dispatch` | сравнения байта команды, длина 32-байтного отчёта, таблица ответов |
| `i2c2_transport` | записи/чтения I2C-регистров, START/STOP, адрес ведомого |
| `gpio_matrix_scan` | повторяющийся цикл по линиям, чтение входов и запись выходов |
| `key_debounce` | маски/счётчики стабильности и переходы состояний |
| `rgb_update` | длинные последовательности записей цветов или таймингов |
| `vial_protocol` | vendor HID dispatch и известные Vial/VIA структуры |

## Ограничение результата

Это восстановление логики, а не получение исходного проекта. Сохранятся
условия, циклы, обращения к памяти и вызовы, но не исходные имена, типы и
комментарии. Поэтому каждое имя будет сопровождаться уровнем уверенности и
xref на подтверждающие инструкции.
